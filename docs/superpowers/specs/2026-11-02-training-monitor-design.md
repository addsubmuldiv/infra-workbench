# 训练任务监控设计草案

日期：2026-11-02。状态：供讨论，尚未实施。本文的阈值和模块划分是设计建议，不代表用户已确认。

## 目标与范围

从已有占卡进程发现候选任务，不要求掌握启动命令，也不要求重启训练。支持单机多卡、多机任务关联、日志进度和异常提醒。自动识别不充分时允许人工补全，并展示判断依据。

首期优先支持 Linux 上的 PyTorch/torchrun；通用 Python 及其他启动器可作为未完全识别的进程组接管。GPU/NPU 共用任务模型，设备进程采集分别适配；NPU 的 PID、rank 和容器映射能力必须实测，不能将 GPU 验证结果视为 NPU 验证。

不在首期实现调度器、自动恢复、自动终止任务、全量文件索引或完整训练框架插件。监控不会自动读取所有用户的日志。

## 当前代码依据

- backend/remote_probe.py：从设备查询得到 PID，并读取用户、父 PID、cwd、命令；读取前后校验 /proc/PID/stat 的启动时间，但尚未把该启动时间返回为持久身份字段。
- backend/app.py：已有 SSH 资源轮询，可复用采集入口；任务增强采集应独立限流，不能阻塞资源总览。
- backend/resource_history.py：已有 SQLite 资源事件；当前精简记录不含稳定进程身份，不能直接作为任务历史。
- backend/log_reader.py：支持带 step/iteration 的 JSON 数值指标、rank 和 step 回退分段；面向有大小限制的完整快照，不适合每轮重读长日志。
- backend/terminal_tmux.py：已有持久终端基础；会话存活不等于训练存活，其状态不能直接当训练退出结果。

## 数据模型：任务、执行轮次、节点分组、进程

Task 是用户关注的逻辑实验，有内部 UUID、名称、类型、关联依据及用户确认信息。默认先生成候选分组；用户点击“监控此任务”后持久跟踪、读取选定日志并启用提醒。

Attempt 是一次执行轮次，容纳本轮进程和日志段。已确认的弹性重启、重新执行生成新轮次，保留历史。没有证据时只提示“可能是重启”，不把同目录的新训练自动接回旧任务。

NodeGroup 是某台物理节点、某个运行上下文中的本地训练分组。ProcessInstance 表示一次进程生命期；进程可以使用多张设备，设备也可以被多个进程共享。

建议身份：

```text
process_key = node_id + boot_id + host_pid + start_ticks
Task -> Attempt -> NodeGroup -> ProcessInstance -> DeviceUsage[]
```

node_id 是去重后的受管节点身份，SSH 配置 ID 只代表连接入口。发现不同入口指向同节点时提示关联，不仅凭 IP 自动去重。boot_id、机器身份等读取失败时标记身份不完整，不把 PID 单独当可靠历史身份。

设备优先用 UUID，分区设备附带实例身份；没有稳定 ID 时保存设备种类、索引和有效范围。rank、设备号、进程数之间不作一一对应假设。

## 从占卡 PID 识别本地任务

1. 沿用设备采集，先按 process_key 去重，保留每个进程的设备关联及显存数据。
2. 有界读取 PID 和祖先进程的结构化 argv、PPID、cwd、启动时间、运行上下文；最多回溯 8 层或 128 个相关进程，达到上限显示证据不完整。
3. 只读取分布式环境变量白名单：RANK、LOCAL_RANK、WORLD_SIZE、LOCAL_WORLD_SIZE、GROUP_RANK、MASTER_ADDR、MASTER_PORT、TORCHELASTIC_RUN_ID、TORCHELASTIC_RESTART_COUNT 等。敏感参数沿用脱敏；不能把完整环境或原始 argv 写入日志、数据库或模型上下文。
4. 识别具体训练启动器实例及其 worker；共享该启动器实例的 worker 自动归组。祖先链必须逐个校验身份，遇到退出、重用或权限不足就停止推断。普通 shell、tmux server、容器 init 不是训练归组根。
5. 进程作为“占卡候选”与“训练候选”分别记录。仅名称为 python、占显存或命令含 train 均不是确认训练的充分条件；推理服务可保留类型“其他计算任务”。

归组规则优先级：

| 证据 | 行为 |
| --- | --- |
| 工作台任务 UUID/经验证的调度器执行身份一致 | 自动归组，保留来源范围 |
| 同一节点、同一训练启动器进程实例的 worker | 自动归为本地组 |
| 无启动器，但分布式执行标识与运行上下文形成完整且无冲突的证据 | 提出可确认的归组建议 |
| 仅 cwd、脚本、用户名、时间相近 | 只提示可能相关，不自动合并 |

命令签名保留关键训练参数，单独提取 rank、节点地址等拓扑参数；不能简单删除所有“看起来不同”的参数。命令签名是辅助证据，不是任务主键。

父进程退出后保留既有历史关系，不因 worker 被重新托管而拆组。后续出现的新 worker 必须重新验证，不能仅凭旧 PPID 数字加入。

识别启动器后有界枚举其相关 worker，包含尚未初始化设备或暂时不占卡的进程；设备列表只是发现入口，不是完整成员名单。枚举受限时保持覆盖度未知，不能据此宣称成员齐全。

容器中区分宿主 PID、容器 PID 和 PID namespace。能经验证映射时关联，不能映射时明确显示“容器进程信息不完整”；不跨 namespace 用数字 PID 拼接。cgroup 是上下文证据，同容器不等于同任务。路径按进程可见文件系统解释，不能直接将容器路径当宿主路径打开。

## 多机归组

先形成各机 NodeGroup，再做跨机关联。每条关联保存规则、证据、冲突及人工决定，用户可以合并、拆分、固定归组；自动推断不能覆盖人工拆分。

强身份优先：未来由工作台分配并跨节点传递的任务 UUID；或具有集群、提交、执行轮次范围的调度器身份。裸 job ID、run ID 不保证全局唯一。

现有 torchrun 任务使用联合证据提出建议：

- 有意义且匹配的 run ID；空值、默认值和常见复用值不当唯一标识。
- rendezvous 参数和 MASTER_ADDR/MASTER_PORT，分别保留，不假定两种 endpoint 必然相同。
- world size、rank、角色信息相容；固定拓扑下 rank 不重复，worker 覆盖范围可解释。
- 脚本/配置特征兼容，观测时间重叠或处于可解释的启动阶段。
- 网络上下文相容；localhost、容器内地址和无法确认的 DNS 别名不跨机器硬匹配。

首期对纯推断的跨机关系默认只推荐，由用户确认。检测到 rank 冲突、配置冲突或多个候选时禁止自动合并。即使强身份一致，冲突也必须暴露。

不要求不同机器上的绝对目录相同；跨机 UID 也不能直接比较。多角色、弹性 world size、流水线并行时按角色及本轮拓扑核对，不用简单“进程数等于卡数”等式判断完整性。

任务覆盖度单列：期望节点/worker 数、已识别数、不可观测数。发现 8/16 个 worker 时显示“已观测 8/16”，不能声称完整监控。没有期望拓扑则显示“期望数量未知”。

示例：A 上 rank 0–7，B 上 rank 8–15，world size=16，run ID 与 endpoint 相符，建议合并；C 即便脚本和目录相同，也不会因这些弱特征加入。B 断连只改变覆盖度；A 退出而 B 不可达时不能判整个任务结束。

## 日志关联

日志是独立来源 LogSource，通过 LogBinding 关联到 Attempt、节点和可选 rank，不把路径直接当任务身份。

关联优先级：

1. 工作台启动时明确记录的日志、进度文件和结果文件。
2. 用户选择并确认的远端普通文件。
3. 已验证进程的 stdout/stderr FD 指向的普通文件，或明确日志参数：作为候选，展示来源、当前写入情况和预览；输出目录参数不等于具体日志文件。
4. 工作目录下有界发现的常见日志：只推荐，不递归扫描整盘。

默认由用户确认外部任务的日志绑定，避免把旧日志、其他任务日志或共享日志当成当前训练。绑定时记录文件身份、基线 offset、已有内容的时间范围；默认历史内容用于展示，不触发当前异常或完成通知。

不读取 pipe、socket、PTY 或 /proc/PID/fd 中的非普通文件，避免消费训练输出或阻塞。tmux 抓屏至多作为人工诊断参考，不能作为可靠进度或结束凭据。无法自动找到日志时仍提供资源与进程监控。

增量追尾新增独立 reader：

- 用文件设备号/inode、offset、尾部片段指纹和文件大小识别替换、截断、轮转，必要时另开日志段。
- 每次每来源默认最多读 256 KiB；过量排队追赶，显示积压与数据新鲜度。超限长行明确记录，不静默当作已解析。
- 保留半行和 UTF-8 解码余量；半行不解析，重启后游标及半行状态可恢复。
- 文件变小、同尺寸内容改写或身份变化时创建新段，记录连续性缺口；轮转后旧文件已不可访问则说明可能漏读。
- 按来源、文件代次和字节位置去重；共享文件跨节点仅在明确知道是同一来源时去重，不比较跨机 inode 来判断共享存储。
- rank、来源、日志段分别保留；不把所有 rank 指标求均值。优先展示用户指定或明确识别的主指标来源。

首期解析现有 JSON 指标格式；另提供版本化文本解析模板，先选真实日志样本覆盖常用训练栈。未知格式仍展示原文，用户可选择模板。step 回退先标记日志新段，可能是重启、续训或日志混入，不直接等价为新 Attempt。

首期以追加日志为支持目标；两次采样之间发生的覆盖写入无法保证全部发现。指纹异常时标记连续性未知，不承诺无遗漏。积压内容没有可信日志时间时，只记录“本次补读发现进度”，不把接收时间当实际推进时间，也不据此宣称当前已恢复。

## 状态：分开保存，不用一个枚举混合所有含义

| 维度 | 值与依据 |
| --- | --- |
| 可观测性 | 正常、部分缺失、过期/不可达；由节点采集结果与覆盖度决定 |
| 生命周期 | 已发现、运行中、结束待确认、已结束（结果未知）、退出码 0、非零退出、确认取消、重启中 |
| 训练结果 | 未知、训练报告完成、有失败证据；独立于启动器退出码 |
| 进度健康 | 推进中、尚无指标、日志静默、疑似停滞、存在异常 |

生命周期规则：

- 占卡列表消失后必须继续跟踪已知启动器和 worker；释放设备不等于进程退出。
- 只在身份匹配的直接进程检查确认缺失时增加退出计数。建议连续 3 次、覆盖至少 30 秒后进入“结束待确认”；超时、权限不足和采样间断都不累计。
- 全部已知成员确认退出且无权威结果时，宽限 60 秒后记为“已结束，结果未知”；若覆盖度不完整，必须同时标明仅已知成员结束、全局结果未知。
- 能取得可信启动器/调度器结果时记录退出码及结果范围。普通 SSH 观察者通常不能补取既有非子进程的退出码。单机 worker 的退出码不代表整个多机任务结果。
- 日志末尾出现异常记录只触发“有异常证据”；可能被捕获或之后恢复。完成文字也只表示“训练报告完成”，不强行覆盖仍存活的进程或其他节点失败证据。
- 退出码 0 可显示“执行成功退出”，不等价于达到目标步数或训练质量合格。取消必须有明确操作或调度器凭据，不能仅凭信号退出推断。
- 仅有强关联身份和 restart count 等证据时标记重启；下一轮不覆盖上一轮日志及失败记录。

健康规则：日志字节增长和有效 step 推进分别计时；loss 改变不作为必须推进条件。step 停滞阈值建议 max(10 分钟, 最近有效 step 间隔中位数的 5 倍)，样本不足时仅用可配置固定阈值。评估、保存 checkpoint 等有明确阶段证据时展示阶段并延长对应阈值。低利用率只能作辅助证据。

默认停滞判断要求进程可观测、日志绑定可信且 reader 已追平；采样断开或读取积压时显示数据过期，不宣称卡死。所有时间区分远端日志时间、中央接收时间和采样区间，不依赖跨机时钟完全同步。

历史异常事件与当前健康分开：traceback、失败轮次等证据保留；在确认出现新的实时 step 推进、明确恢复或新 Attempt 后，当前异常可解除，并记录恢复事件。不能因曾有异常让任务永久保持当前失败状态。

## 采集、持久化与接口

资源轮询仍负责发现占卡 PID。任务增强采集只针对新 PID、已监控进程及有限祖先；稳定字段缓存，进程存活和日志按约 10 秒采集。此为初始预算，需实测 SSH 延迟与规模。

每机批量执行探针、并发限流、超时及退避；同一进程只增强采集一次。没有占卡的已监控进程继续检查。所有不可用字段携带原因，不能把缺失当空集合。

SQLite 建议新增 tasks、attempts、node_groups、process_instances、memberships、log_sources、log_bindings、log_cursors、metric_points、task_events。关联关系带有效时间、证据、规则版本和人工覆盖；原始观测与推导状态分离。

游标推进、对应指标及事件落库在同一事务中提交，失败可重复采集且不重复通知。只存选定指标和有界事件片段，不复制全部日志。原始日志继续留在服务器。指标按保留策略降采样；任务摘要保留至用户删除。

建议新增 training_probe.py、training_grouping.py、training_logs.py、training_state.py、training_store.py、training_routes.py。通过独立调度入口接现有 SSH 与通知服务，不将复杂推断塞进资源 compact 逻辑。

接口覆盖候选列表、接管监控、归组预览及确认、拆分、日志候选及绑定、任务详情、指标及事件、停止监控。停止监控仅停止追踪，不停止远端训练。预览与确认间校验观测版本，避免对过期 PID 进行关联。

后台持续运行时收集并通知，关闭前端不影响；整个工作台后台停机时不能继续监控，重启记录观测缺口，不承诺补齐期间短暂故障或进程。

通知按 Task/Attempt/异常类型去重，区分新异常、恢复及再次异常。默认关注已接管任务，机器不可达聚合通知，避免逐 worker 轰炸。

## 使用流程

任务页分“正在监控”和“发现的候选”。候选卡显示识别类型、用户、节点与设备、分组理由及缺失信息。接管时可命名、确认成员、选择日志和主指标来源。

详情页展示任务/执行轮次、覆盖度、四维状态、主进度曲线、节点/rank 表、日志与事件时间线，并能打开原有文件窗口及终端。状态旁能展开“为什么这样判断”。不确定的跨机关联提供“合并建议”，不偷偷更改成员。

## 交付顺序与验收

第一阶段：稳定进程身份、本地归组、手动跨机合并/拆分、日志手动绑定、JSON 增量追尾、状态及提醒。先用真实单机与双机任务验证端到端价值。

第二阶段：torchrun 联合证据跨机推荐、stdout/stderr 普通文件候选、常用文本日志模板、重启与拓扑变化。与第一阶段共用模型，不另建任务体系。

第三阶段：工作台启动记录 UUID、命令及结果；跨机启动需独立全局结果协议。调度器、容器和 NPU 深度适配按真实环境补充，不阻挡外部任务接管。

必要验收：同目录并行两次训练不误合并；一进程多卡只计一次；跨机 rank 冲突阻止合并；默认 run ID/localhost 不产生跨机关联；PID 重用及机器重启不串任务；父进程退出不破坏已知关系；GPU 释放而进程存活不报结束；SSH 断连/权限下降不报成功或退出；轮转、截断、半行、UTF-8、重复采样和后台重启不重复指标；旧日志完成标记不结束新任务；单 rank 失败与全局结果分开；读取积压不误报停滞；手动拆分不被后续自动归组合回。

## 待真实环境验证

- 常用启动器及训练框架的真实 argv、环境变量、日志样本。
- 是否存在容器 PID 映射、sudo 或 /proc 权限限制。
- 多机是否都有受管 SSH 入口，是否共用日志存储，弹性训练是否常用。
- GPU/NPU 各自的进程列表完整性、延迟及读取成本。

这些问题影响适配覆盖范围，不改变“自动发现、证据归组、人工补全、状态分层”的基本模型。
