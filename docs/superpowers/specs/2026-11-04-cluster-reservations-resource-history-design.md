# 集群预约与资源历史统计设计

日期：2026-11-04。状态：方案已批准，首版功能已实现并通过自动化回归，真实长期采样效果仍需持续观察。

配套界面示意：[打开交互稿](../../designs/2026-11-04-resource-planning.html)。其中的机器状态、时间和数字均为示例，不读取真实后台。

## 1. 要解决的问题与范围

用户需要两类能力：在几台指定机器或集群中任意几台同时具备资源时收到一次提醒；回看某台机器一天的哪些时段空闲、空闲多少张卡，并明确看到没有可靠数据的时段。

沿用现有本地后台、SQLite、React、集群与系统/邮件通知。预约继续用于提醒，不锁定设备，不限制其他人使用，不自动启动训练。第一版不做多用户抢占、排队优先级、未来日历时段预订、任务调度或根据历史预测未来。

目标机器仍为当前支持的 Linux GPU/NPU 机器；历史和预约不需要识别跳板系统，也不增加远端常驻 Agent。

### 现有实现依据

- `backend/reservations.py`：单机指定设备/按数量预约、连续空闲计时、完成与通知事务。
- `backend/clusters.py`：集群 ID、revision 和机器成员；当前集群主要用于批量命令与终端。
- `backend/resource_history.py`：变化事件和最新基线，保留 7 天/10000 条；不足以重建可靠的全天数量曲线。
- `frontend/src/main.tsx`：算力总览、卡预约、精度对比、设置；已有集群侧栏。
- 现有历史事件保持原用途，不把它们补算成新增统计数据。

## 2. 共用的资源状态与统计口径

### 2.1 “可用设备”的定义

区分“客观空闲状态”和“能否满足预约”。历史统计只记录客观空闲数量，不要求用户设置预约条件。两者共用基础状态检查，预约再附加数量与显存门槛：

1. 设备类型与选择的 GPU/NPU 一致。
2. 可见计算进程信息完整，且没有计算进程。
3. 计算利用率为有效数值且等于 0。
4. 预约额外要求剩余显存达到门槛，默认 1 GiB；历史不以显存门槛筛掉空闲设备，显存余量作为独立详情。
5. 健康状态不为 Alarm；Warning 延续现有规则，计入但附警告。

当前 GPU 的 health 常为 `unknown`，沿用现有“仅 Alarm 排除”的行为；health 未知本身不单独阻止 GPU 被判可用。进程、利用率、显存等必要字段仍按三态处理，不能用健康字段未知作为跳过其他检查的理由。

每个设备判为“可用”“不可用”或“未知”。只要有已确认的排除条件（例如存在进程、利用率 >0、Alarm、显存不足），即可判为不可用；没有排除证据、但必要字段缺失，判为未知。采集失败、数据过期、设备身份无法确认时，不能使用旧值确认可用。

这里的空闲主要指 GPU/NPU 可用，不代表 CPU、网络、存储或互联拓扑也满足分布式训练要求。历史页面使用“空闲设备”，提供固定口径说明；数量和显存要求只在预约页面设置。

NPU 多芯片沿用当前设备编号口径：统计的是采集设备/逻辑芯片数，不擅自换算物理卡数。界面默认写“个设备”，在已确认一设备对应一卡的情况下才用“张卡”。GPU 与 NPU 单独统计，不能混成“8 张卡”。

### 2.2 时间有效性：按采样确认，不承诺瞬时真实状态

- 使用后台接收并验证完成的采样时间作为 `observed_at`，UTC 秒存储；不使用目标机器时钟。
- 同次采集记录开始、结束时间和耗时，保留“这是区间采样”的限制。
- 样本向后生效，不向前推断；两次采样之间的变化只能定位到采样分辨率。
- 默认最大观测年龄 `freshness_seconds = max(45, refresh_interval_seconds + 40)`。10 秒刷新对应 50 秒，30 秒刷新对应 70 秒。该数值是本设计的工程默认值，用来容纳本轮最长 35 秒命令等待及少量调度延迟，应集中配置并写入样本，不由前端猜测。
- 保守计算截止时间 `fresh_until = collection_started_at + freshness_seconds`，采集耗时包含在年龄中，不从完成时重新赠送一整段有效期。若完成时已过截止时间，该结果不进入可用状态；UI 区分“最近完成采集时间”和“观测年龄”。
- 同一次后台运行内，将样本从 `observed_at` 延续到下一条结果或 `fresh_until`，两者取早。失败结果到达时立即截断此前状态，从失败时间起记为未知，不追溯猜测失败期间的真实状态。
- 程序正常退出时截断到退出时刻；异常退出或电脑休眠只能延续到最后样本有效期，之后未知。新进程必须有新的 `run_id`，不跨重启续接旧状态；无法知道的异常退出具体时刻不伪造。
- 调整刷新间隔后只影响新样本，历史样本继续按记录时的有效期解释。
- 定时任务检查过期状态，即使某台机器一直没有采集回调，预约也会变为未知并停止计时。

这些规则把“不知道”和“空闲”分开，同时也意味着有效期内的短暂变化可能未被发现。页面说明“根据采样估计，时间精度受刷新和采集耗时影响”。

## 3. 集群预约

### 3.1 三种入口，一套预约中心

原“卡预约”更名为“资源预约”，保留旧单机预约和链接。新建窗口顶部有三种方式：

| 方式 | 选择项 | 成立条件 |
| --- | --- | --- |
| 单台机器 | 现有指定设备/任意数量 | 保持现有单机规则 |
| 指定多台机器 | 从集群或全部机器中勾选至少 2 台 | 所有指定机器同时满足各自条件 |
| 集群内任意几台 | 选择集群、所需机器数 N | 候选机器中至少 N 台同时满足各自条件 |

集群侧栏菜单新增“预约资源”；算力总览选中多台机器后新增“预约所选机器”。入口只预填表单，不自动提交。

### 3.2 设备条件和表单

通用条件：设备类型 GPU/NPU、每台至少空闲设备数 K、每设备最低剩余显存、连续满足时间、系统通知、可选邮件。默认连续满足 2 分钟，范围沿用 0～1440 分钟。

“指定多台”先设置通用条件，也允许展开某一行单独调整设备类型、K 和显存门槛。第一版多机模式按数量选设备，不提供逐机指定卡号；精确卡号仍用现有单机预约，避免让新建窗口变成复杂设备矩阵。

“任意几台”对所有候选使用同一类型、K 和显存门槛，不自动混用不同型号。候选列表显示型号与每机设备数，允许排除个别机器。不同型号仍可手动保留，但摘要明确“未限制型号/互联条件”。第一版不增加新的跨型号性能换算。

创建时检查 ID、类型、数量、有限数值、设备容量与作用域。K/N 不能超出已确认容量；容量未知的候选允许加入并显示“容量待确认”，运行期间记未知，不能据此满足条件。全部候选都无已确认容量时提示并要求先完成一次有效采集。指定多台有确认设备不足的机器时必须修改条件；任意模式至少应有 N 台已确认或待确认可能满足的候选。

提交按钮上方总能看到自然语言摘要，例如：“机柜 4 的 8 台候选中，任意 2 台，每台至少 4 个 NPU、每个剩余 ≥32 GiB，连续满足 2 分钟后提醒一次。”

### 3.3 集群成员变化

创建时保存集群 ID、名称、revision 和完整候选 ID 列表。预约候选集合固定，不因后来加入集群的机器自动扩大；从集群移出的机器不自动移出已保存的预约。

集群 revision 变化后列表显示“集群成员已变化，当前仍按创建时的候选范围监测”，提供“查看差异并更新范围”。更新范围是显式编辑，重新验证并重置计时。机器真正从工作台删除时，指定模式进入“需调整目标”；任意模式可以继续使用剩余候选，但剩余数量不足 N 时进入“需调整目标”。集群删除后保留预约的候选快照与名称，显示“原集群已删除”，仍可编辑或取消。

提交携带 revision，后台发现保存前已变化时返回 409，前端保留草稿、刷新差异，不静默提交旧选择。

### 3.4 “同时满足”与计时

每台机器有 `ready / not_ready / unknown` 状态。只用各自新鲜样本，在每次相关采样和过期检查时聚合；不要求所有机器恰好同一秒采样，也不宣称原子资源快照。

指定模式：全部 ready 才开始/维持计时；任何 not_ready 则等待；没有 not_ready 但存在 unknown 时为数据未知。

任意模式：

- ready 数 ≥N：开始/维持计时，其他机器的未知或失败不打断。
- ready 数 <N，但 ready+unknown ≥N：数据不足，重置计时并显示未知。
- ready+unknown <N：明确不足，重置计时并等待。
- 符合条件的具体机器可以替换，只要每次确认都有至少 N 台 ready。该语义在表单和说明中明确写出；需要固定机器的用户使用指定模式。

只有聚合条件不再明确成立时才重新计时，不把中断前后的分钟数相加。候选样本过期会触发重算，但任意模式仍有 N 台明确 ready 时不重置。计时依据单调时钟，持久化时间仅用于显示；重启后保留规则、从新样本重新确认。

创建、编辑后的旧样本不能启动新规则的计时。指定模式需全部指定机器各有一份规则生效后的有效样本；任意模式需至少 N 台有这样的有效样本，无需等待其余候选。等待设为 0 也遵守此要求。

确认窗口结束时重新校验所有目标新鲜度及资格，在同一事务中保存完成状态、匹配机器/设备快照、事件、系统通知 outbox 和可选邮件 outbox。用预约 ID 唯一约束防止重复提醒。匹配优先当前连续满足较久的机器，同分按稳定 ID；设备按稳定编号取前 K 个。结果解释是“提醒时可用”，不承诺点击通知后仍空闲。

### 3.5 状态与通知

预约卡片显示：模式、来源集群或指定机器、候选数/所需数、每机设备条件、当前 ready/not_ready/unknown 数、连续确认进度、最近采样时间。展开后逐机显示原因，如“3/4 个设备符合”“采样超时”“数据已过期”。

状态为：等待资源、正在确认、数据不足、需调整目标、已提醒、已取消。已取消保留历史，可删除；已提醒仅再次预约，不回退为等待。编辑重置计时。

通知正文列出满足条件的 N 台机器及每台实际匹配设备，点击打开预约详情并定位这些机器；用户再打开某台机器。不能借用单机 `host_id` 链接造成只显示第一台。邮件沿用现有凭据和发件设置，单独展示提交/失败回执；系统通知被接受不等于已阅读。

## 4. 资源历史与统计

### 4.1 页面与查询条件

新增一级页面“资源历史”，位于资源预约之后。机器卡片新增“查看历史”；集群菜单新增“查看资源历史”。从这些入口进入时预填目标，历史页面拥有独立的筛选状态，不修改总览的机器选择。

默认看单台机器、今天，支持前一天/后一天、日期选择、最近 24 小时、7 天。单日图按显示时区的自然日，默认电脑时区；示意稿使用 Asia/Hong_Kong。服务端接收明确 IANA 时区和日期，换算实际 UTC 边界；夏令时日按 23/25 小时处理，导出同时保留 UTC 与偏移。最近 24 小时是滚动窗口，不冒充“今天”。

范围可选单机/多机/集群。GPU/NPU 分开选。历史页只提供机器范围、日期和设备类型筛选，不提供每台至少 K 个设备、最低显存或连续满足时间等预约条件。空闲定义作为只读说明，不占据一行配置表单。

集群历史默认使用当前成员，明确标记“按当前成员回看”；机器移入前的数据仍属于该机器，不伪装为当时的集群利用率。已删除机器可从历史归档中查询，保留采样时名称；删除历史是单独操作。

### 4.2 主视图：一天的可用设备数

顶部四个指标：整机全部设备空闲时长、已确认空闲设备小时、平均空闲设备数、完整采集覆盖率。整机空闲明确指所选类型的所有设备均已知且空闲，不代表 CPU/网络/存储状态。没有可确认的设备库存时显示未知，不把零设备当作整机空闲。

主图采用阶梯时间轴：横轴时间，纵轴设备数量，填色显示已确认可用数；未知部分用灰色斜纹表示。图例、悬浮和可访问文本共同解释状态，不只依赖颜色。不画数量阈值线、不判断“够不够用”，用户直接查看各时段空闲数量。

全部样本未知的区间不画成 0。部分设备未知时，展示已确认可用数 L 和可能可用上界 U=L+未知数；可用区用实色，未知数量用斜纹叠加。例如“可用至少 3/8，另 2 个未知”，不显示精确“空闲 3 张”。

图下是时段列表：开始/结束、持续时间、确认可用数或范围、数据完整性、未知原因。合并状态和数量相同的相邻区间；不能跨未知/设备集合变化拼接。点击某段查看设备明细、首末样本和该段已知异常，支持跳转对应资源变化事件。

第二层可展开每个设备的“可用/不可用/未知”条带。单机设备超过 16 个时纵向滚动；7 天视图按日分组，不压成无法辨认的小条。

### 4.3 聚合口径

任意时间 t 显示已确认空闲数、已确认非空闲数和未知数。部分设备未知时，空闲数是下界，页面显示“至少空闲 3 个，另 2 个未知”；库存未知时不猜总设备数。

- 整机全部设备空闲时长：所选类型的库存已确认、设备数大于0、全部设备状态已知且空闲的时间积分。任何设备未知都不能计入。
- 空闲设备小时：对已确认空闲设备数按时间积分；存在未知时标注为保守下界，不推测完整总量。
- 平均空闲设备数：只在所有目标设备状态完整的区间做时间加权平均，并显示这些区间的时长。没有完整区间时显示“无完整数据”，不用采样点算术平均。
- 完整采集覆盖率：所有目标设备状态已知的时长 / 已经过去的查询时长；当日未来不进分母，历史完整日使用实际23/24/25小时长度。
- 详情提供最长整机全部空闲时段、逐段空闲数量和未知原因。第一版不默认展示一个可能隐藏缺失的“全天空闲率”。

示例：0–4点空闲8个、4–8点空闲0个、8–10点未知、10–14点空闲6个、14–16点未知、16–24点空闲2个，则整机全部空闲4小时、已确认空闲72设备小时、完整时段平均空闲3.6个、完整采集覆盖率83.3%。

多机/集群视图每台一行，对齐显示空闲设备数量，而不是“是否达到某个预约条件”。主图必须先展示“每个时段空闲几台机器”：两条数量时间线分别为全部设备空闲的机器数、至少1个设备空闲的机器数（后者包含前者，不可相加）。同时标记未知机器数；全部未知时断线并画斜纹，不能画成0台。点击任一时段显示整机空闲、部分空闲、均占用、未知四类互斥机器数，合计等于目标机器总数。下方逐机条带在色块内直接标空闲设备数量，并有共享时间刻度，不再仅用绿色/灰色表达。已确认空闲设备总数、未知设备数和完整采集机器数放到该时段详情。不同设备类型分开；各机器不同时段的空闲不能当作同时空闲。需要“任意N台、每台K个”的用户从预约页设置，历史页不重复放一套预约配置。

### 4.4 缺失原因和边界

未知原因包括：尚未开始记录、采集失败、样本过期/采样间断、设备字段不完整、设备集合变化、后台未运行。无法区别异常退出、休眠或网络长时间卡顿时用“采样间断，原因未确认”，不能编造精确原因。

第一次有效采样之前未知；今天未来时段为“尚未到达”，不算覆盖率分母。程序升级前的数据没有数量采样，标“尚未开始记录”，不从旧变化事件补齐。清理保留期前为“超出保留范围”，不同于网络掉线。

同一编号设备 UUID/芯片标识改变时分开记录，不跨设备身份变化延续；设备增减会更新库存段和分母，不把新增设备追溯算到之前。时钟回拨产生冲突时停止延续并建立新时间段，预约计时仍使用单调时钟。

### 4.5 保留与导出

第一版默认保留 30 天，可选 7/30/90 天，设置中显示当前占用和清理范围。清理任务分批执行；缩短保留期需要具体确认将删除的日期范围。原有 7 天变化事件策略独立，历史统计不依赖事件是否被清理。

导出当前范围 CSV：逐时段数据和摘要分两份。包含目标范围、设备类型、时区、规则版本、覆盖率、未知时长、设备单位；逐段包含 UTC/本地开始结束、库存、确认可用数、未知数、状态和原因。导出之前限制时间跨度/机器数量，避免一次载入全库。

## 5. UI 结构与交互细节

## 6. 数据模型、接口与集成

### 6.1 数据层

新增独立历史数据表，避免给原变化事件改含义：

- `resource_observations`：host_id、run_id、observed_at、collection_started_at、status、reason、fresh_until、rule_schema_version、紧凑设备数据（设备身份、类型/型号、空闲显存、利用率、进程是否已知/是否存在、health）。不存密码、完整进程命令或日志。
- `resource_inventory_epochs`：设备身份集合、起止观察时间，处理新增/移除/替换及单位。
- `resource_recording_runs`：启动、正常结束、异常结束未知标识。
- `resource_availability_segments`：由采样生成的查询缓存，保留原始判定字段及数量变化，不能只缓存默认阈值结果导致用户换门槛后无法查询。

权威数据为 `resource_observations` 和库存/运行边界，不是图表缓存。只有重算所需的全部字段（包含显存原值、利用率、进程已知标志与有无进程、health、身份、有效期规则）完全相同，且样本序列连续时，才可用无损连续段代替重复 payload；仍保存每次观测的序号、起止时间与新鲜度证据。显存逐次变化时保留原值，不按默认阈值或四舍五入后的值合并。`resource_availability_segments` 可从权威数据重建。容量估算按未压缩的每采样设备数量进行，不能假定压缩一定显著节省空间。

数据写入通过有界队列/批量事务隔离；每机分配递增采样序号。队列溢出或写入失败时记录待补写的序号缺口；下一次成功写入先截断旧连续段，落下 `history_write_gap` 区间，再记录新样本。不允许把丢失样本两侧的空闲段直接连接；连缺口元数据都无法持久化时，下一次启动从持久化序列和 run 边界保守判定未知。显示历史不完整告警和覆盖损失，不把成功 SSH 采集改成失败。实时预约直接消费验证后的内存样本，不依赖历史写队列。

查询按 host_id+time 索引，图表返回限量段；屏幕像素级聚合必须保留 min/max 和未知比例，不把短未知平滑掉。摘要在完整区间上计算，不用降采样图表值算统计。

新增 `group_reservations`，不强行把多机放进旧单机 `host_id` 字段：id、mode（specified/cluster_any）、cluster_id/revision/name_snapshot、candidate_host_ids、per_host_conditions、required_hosts、wait_seconds、notification_channels、status、时间和最终匹配快照。运行中的逐机资格和计时证据独立于历史展示缓存。

单机和群组预约共享条件判断、状态展示、通知 outbox 逻辑；原单机数据不迁移、不丢失。完成与通知记录同事务，邮件格式增加多机模板。规则版本与设备身份写入匹配证据。

具体集成要求：扩充 `backend/reminder_links.py:event_link()` 的合法站内路由，支持经过参数校验的 `#reservations?group=<id>`，前端打开对应群组详情，旧单机链接保持可用。群组邮件 payload 使用显式 `type=group_reservation`、模板版本、group_id、候选摘要与 `matched_hosts[{host_id,target,devices,conditions}]`，不伪造单机 target/labels。`MailService.prepare/message` 按类型生成模板。群组完成事务要与 events、desktop_outbox、mail_outbox 使用同一 SQLite 连接/事务；不能先调用会自行提交的旧 `save_with_events` 再另存新表。

### 6.2 拟定接口

| 接口 | 用途 |
| --- | --- |
| `GET/POST /api/group-reservations` | 列表/新建，POST 需要请求幂等键 |
| `GET/PATCH /api/group-reservations/{id}` | 查看/编辑；PATCH 携带预约 revision 防止覆盖 |
| `POST /api/group-reservations/{id}/cancel` | 取消并保留记录，重复取消幂等 |
| `POST /api/group-reservations/{id}/rebook` | 新建独立 ID，不覆盖已提醒证据 |
| `DELETE /api/group-reservations/{id}` | 删除已取消/已提醒记录；运行中的规则先取消 |
| `GET /api/resource-history` | 单机/多机的区间、摘要、设备库存、coverage 与限制 |
| `GET /api/resource-history/export` | 流式导出当前查询结果，有限范围 |
| `GET/PUT /api/settings/resource-history` | 保留期、记录状态和存储用量 |

历史参数：host_ids、from/to 或 date+timezone、kind；不接受预约数量和显存阈值参数。自然日参数和绝对时间参数互斥；from/to 使用半开区间。默认最多 31 天和 100 台，超过范围分批。7 天概览可以按日分页，90 天保留不意味着一次画 90 天全部设备。

统一返回计算规则版本、实际UTC边界、有效期、记录起点、保留起点、样本数量、未知原因时长、是否截断和统计限制。查询失败不可返回全 0 的成功结果。

写接口沿用本机鉴权/X-IWB 校验。AI/MCP 后续同步提供新建/编辑/取消群组预约、查询历史工具，使用同一服务层；必须验证全部候选都在授权机器范围内，集群查询不能绕过 scope，历史按授权目标过滤。工具返回结构化事实，不能推断未知区间为空闲。

## 7. 验收与验证

预约：指定两台同时满足；任意 N 台匹配成员替换；部分未知但仍有 N 台明确符合；未知导致不足；任一资格过期；wait=0 仍需新确认；重启不延续；修改/成员变化/删除；型号和单位展示；多次并发回调只发一次；取消后不通知；邮件失败不回滚已满足状态；权限限制和 revision 冲突。

历史：全天状态变换；首个样本前未知；有效期跨界且包含采集耗时；失败立即截断；重启不跨段；断网后恢复；队列丢样与写库失败形成未知缺口；部分设备未知的空闲下界与未知数；按时间积分而非按样本平均；未来不进分母；23/25小时自然日；设备替换/新增；保留期与新功能上线边界；显存不影响客观空闲数量；不同GPU/NPU分开；多机不同时间空闲不误计同时满足。

前端：全未知、无库存、部分未知、窄窗口、长机器名、批量机器选择、重复提交、加载失败、深链接、键盘操作、中文/英文和主题。通知回到多机详情，旧单机通知不回归。

性能：用 20/100 台、每机 8 个设备的合成数据测 30 天写入量、单日/7日查询、保留清理、后台事件循环延迟；发布前记录实测值，不在设计阶段承诺固定容量或响应时间。观察至少一次包含真实采集失败和恢复的长时间运行。

## 8. 实施顺序与待评审默认值

第一版必须完成：三种预约方式、统一设备条件、群组持续判断/通知/详情、单机/多机/集群单日历史、数量曲线与未知区间、两种覆盖率、默认30天保留、现有单机兼容、中英文和安全验证。

后续增强（本设计保留接口和交互方向，但不作为首版交付前提）：7天批量概览、7/90天保留设置、CSV导出、指定多台逐机不同条件、AI/MCP新工具。逐设备条带可先按需加载。示意稿中的导出和相关控件表达完整目标，不代表这些增强已实现。第一版指定多台先统一每机条件，结构预留逐机覆盖字段。

1. 统一可用性判定、样本有效期和数据测试；建立历史采样存储，先开始积累新数据。
2. 历史查询、准确积分、未知区间、保留与导出；完成单机历史页面，再接多机/集群。
3. 群组预约状态机、周期过期检查、一次性通知和权限；完成预约中心和新建窗口。
4. 集群侧栏入口、通知深链接、AI/MCP、双语、端到端与真实机器验证。

本方案由设计者提出的默认值：历史保留 30 天；默认显示今天；默认使用电脑时区；预约默认显存门槛 1 GiB（历史无此门槛）；新群组预约按数量选设备；任意N允许具体机器替换；预约候选固定到创建时快照；显式编辑范围重新计时。以上均可在评审时调整。

设计阶段只交付示意稿；随后用户已批准实现。首版现已增加生产接口、数据库记录与页面，但未为用户创建真实预约。历史从新后台启用后的采样开始积累。

## 评审修订（2026-11-04）

按用户反馈，历史页取消整行预约条件配置。它只展示客观的空闲数量与时间统计；数量、显存和连续时间条件只在预约中设置。UI示意稿同步调整。

集群历史 UI 补充：先看按时间变化的空闲机器数量，再查看每台机器空闲设备数。只有逐机条带不算完成集群统计设计。示例聚合值必须由与条带相同的数据计算，避免上下图数字矛盾。

### 集群历史热力图修订

逐机条带使用带数量图例的热力图，横轴时间、纵轴机器。使用单色绿色顺序色阶：0个为空浅色，空闲越多颜色越深；示例8设备机器提供0～8的逐级色块图例。每格保留精确数字，悬浮/键盘聚焦显示时间、空闲数、总设备数和未知数。未知用灰色斜纹及问号，不占用0的颜色，避免把“没数据”看成“都忙”。

同一视图所有机器使用统一的绝对数量色阶，不按每台自己的总量归一化，防止4个空闲与8个空闲显示相同颜色。设备总数不同时每行另标容量；色阶上限按本次范围确定并固定到用户改变查询范围，高密度图可使用明确标注的数量分档，但格子/悬浮继续给精确值。部分未知显示确认空闲下界与未知标记，不将未知填入绿色强度。上方的空闲机器数量汇总保留，用来回答某一时段有几台整机或部分空闲；热力图用于定位是哪些机器、有几个设备空闲。

### 集群数量图修订：使用互斥分类，取消包含关系双线

上方机器数量图改为按时间的四类堆叠图：整机空闲、部分设备空闲、无空闲设备、数据未知。纵轴固定写“台机器”，各类互斥且合计等于候选总数，图例常驻，每个时段直接标数量。整机空闲用绿色，部分空闲用琥珀色，无空闲用灰蓝色，未知用灰色斜纹。选择某时段后下方显示完整分类计数。部分设备未知、无法确定属于前三类的机器归入数据未知，不能伪装成部分空闲；已有明确空闲和明确不空闲证据时可确认部分空闲。该修订替代前文关于有包含关系的绿/紫双线的描述。下方设备数量热力图继续按0～8绿色深浅表达，图题与单位保持分离。

### 视觉修订：圆角玻璃质感

数量堆叠图和逐机热力图统一为低饱和、半透明的玻璃表面。数量图的整个绘图区用同一圆角裁切，不给每个堆叠段分别做圆角以免制造间隙；外层容器亦圆角。整机空闲为半透明鼠尾草绿，部分空闲为柔和雾紫，无空闲为低对比蓝灰；固定图例同步，类别不只靠颜色辨认。热力图使用由浅至深的半透明绿色，图例与格子同源，整行条带圆角并加轻微内高光。数字保持不透明，未知继续使用独立灰色细斜纹。玻璃效果只作用背景，不对数字使用 opacity 或模糊；不支持 backdrop-filter 时仍有完整渐变、边框和文字的降级效果。此修订替代上一版琥珀实色方案。

视觉评审最终修订：用户不需要凸起质感。采用平面半透明色块和圆角，去除玻璃高光、内外阴影、浮雕边框及模拟受光渐变。图例、数量图、热力图使用同一平面风格；本条覆盖前述高光与内阴影建议。

视觉参考确认：采用用户提供的选中时间按钮样式——淡色半透明填充、细边框、小圆角。图表保持分类色，热力图保持数量色阶，统一表面处理；无高光、投影或浮雕。

热力图视觉细化：逐时段格子本身也使用参考按钮的淡色半透明底、1px细边框、约7px圆角与细小间距，不只是整行加外框；图例同源，未知格保留斜纹。
