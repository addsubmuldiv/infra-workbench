# 第二轮共享前端性能优化与实测

测试日期：2026-10-31。本次在 `desktop-entry` 分支继续优化网页、桌面共用的前端。

**已确认的收益是减少无变化轮询的页面更新成本，并降低内存占用。启动和多终端延迟没有显示一致改善，不能称为所有操作都变快。**

## 改了什么

1. 每两秒仍读取完整状态，保留在线/过期状态判断和通知检查；相同 JSON 子树复用已有对象，无变化响应不再反复更新整棵 React 页面。`server_time` 在当前界面仅用于首次就绪判断，因此它单独变化不会触发页面更新。设备统计与筛选结果按依赖缓存，分类统计展开时才计算。
2. 终端窗口拖动期间停止保存位置，结束、取消或视口调整后保存最终位置。没有改变终端连接、日志保留和远端窗口调整协议。
3. 加入可选 WebGL 实验，按当前标签创建 GPU 渲染器，标签隐藏后释放；导入失败、初始化失败和 GPU 上下文丢失时回退到 DOM。默认继续使用 DOM。插件的上下文丢失通知会先等待约三秒，给浏览器自行恢复的机会。
4. 精度对比、文件浏览、设置、AI 助手页面改为按需加载；精度对比首次打开后的页面缓存仍保留。构建目标明确为 ES2020 / Safari 15；缺少 `crypto.randomUUID` 时使用加密随机字节生成 UUID，终端代码不再依赖 `Array.at`。

## 测试条件

- 同一台 Windows 11、i5-13600KF、20 个逻辑处理器、约 64 GiB 内存；可见 Edge 与真正的 Tauri Release WebView2 窗口。
- 优化前后各自冻结一份生产前端；对应的页面专项与完整负载测试检查了相同前端 SHA-256。两次对照的浏览器/引擎版本一致，实际视口均为 1440×900，页面可见。
- 48 台模拟机器、384 个设备；真正的本地 WebSocket 向真正的 xterm 输入 ANSI 日志。4 个终端总计 256 KiB/s 持续45秒，8 个终端总计 1 MiB/s 持续60秒，各客户端三轮、轮次中交替客户端顺序。
- Python 后台已就绪且两端共用，不计入客户端差值；未测试操作系统缓存清空后的冷启动、首次 Python 解包或真实远端 SSH 网络极限。
- 内存统计整个客户端进程树的私有工作集，单位 MiB；它与私有提交内存含义不同。报告未把各进程 RSS 简单相加。
- 基线前段曾并行执行少量短回归检查；没有在正式负载期间执行前端构建或完整测试套件。细小的时延、CPU 差值应谨慎解释。

## 页面刷新与首屏

静态数据专项在页面就绪后观察13秒，仍每两秒轮询。下表为三轮中位数。

| 指标 | 桌面：优化前 → 后 | 网页：优化前 → 后 |
|---|---:|---:|
| React 提交次数 | 7 → 1 | 7 → 1 |
| 累计脚本执行时间 | 150.49 → 9.43 ms | 193.44 → 9.42 ms |
| 200 次鼠标移动期间的位置保存 | 200 → 0 | 200 → 0 |
| 同一次拖动包含松手后的总保存次数 | 200 → 1 | 200 → 1 |
| 首屏 JS + CSS 未压缩体积 | 519,544 → 379,787 字节 | 相同 |

首屏 JS + CSS 减少约26.9%。这里排除了测试注入脚本，统计真实首屏资源；可选功能的代码在首次打开对应页面时加载。

13秒内的累计脚本时间不是一次操作耗时，也不代表整个软件快了十几倍。React 提交也不等于整个页面重新绘制。资源数据发生变化时仍需更新页面，不能将静态数据专项的降幅推广到每次真实采集。

拖动脚本耗时没有在两端出现一致改善：桌面中位数108.03→99.30ms，网页88.14→102.12ms，轮次范围有重叠。本项确认减少了同步存储写入，不宣称已经提高拖动帧率。

## 内存

三轮中位数，整个客户端进程树的私有工作集：

| 场景 | 桌面：优化前 → 后 | 网页：优化前 → 后 |
|---|---:|---:|
| 总览空闲 | 194.00 → 155.02 MiB | 214.55 → 189.56 MiB |
| 4 终端持续输出 | 424.54 → 388.49 MiB | 437.64 → 420.70 MiB |
| 8 终端持续输出 | 518.34 → 475.90 MiB | 531.65 → 508.04 MiB |

空闲时桌面减少约20.1%、网页约11.6%；八终端时分别减少约8.2%、4.4%。这些是本次合并优化的观测结果，没有单独隔离各项改动的内存贡献。

空闲轮次范围：桌面优化前185.33–207.69、优化后150.62–159.02 MiB；网页优化前199.61–223.18、优化后179.18–197.23 MiB。八终端桌面为500.93–530.15→472.16–483.24 MiB，网页为502.20–531.99→494.45–515.46 MiB。后者仍有范围重叠。

## 启动

从客户端进程启动到机器列表出现、字体就绪并经过两帧；每次等待宿主和引擎子进程全部退出。下表为五次后续独立启动中位数，新配置单次首启不用于判断胜负。

| 客户端 | 优化前 | 优化后 |
|---|---:|---:|
| 桌面 | 2.381 秒，范围1.367–2.807 | 1.585 秒，范围1.246–1.797 |
| 网页独立窗口 | 1.144 秒，范围0.906–1.355 | 1.306 秒，范围0.841–1.385 |

**不能把桌面这次的启动降幅直接归因于前端拆包。** 页面导航到就绪的中位数没有下降：桌面379.70→397.20ms，网页563.30→686.30ms；变化较大的部分发生在导航之前的估算差值中。这个差值包含尚未分别测量的宿主初始化和系统调度等成本。Rust 启动逻辑没有改动，两组时间范围也有重叠。本次没有证实稳定的整体启动提速。

## 持续输出

表中每项延迟为三轮各自 P95 的中位数。写入回执测到 xterm 写入回调完成，不等于字符最终呈现在屏幕上的时间。

| 指标 | 桌面优化前 | 桌面优化后 | 网页优化前 | 网页优化后 |
|---|---:|---:|---:|---:|
| 4 终端写入回执 P95，ms | 3.43 | 4.72 | 4.22 | 3.27 |
| 4 终端标签切换 P95，ms | 18.5 | 18.7 | 16.7 | 17.7 |
| 8 终端写入回执 P95，ms | 6.79 | 10.14 | 12.88 | 6.36 |
| 8 终端标签切换 P95，ms | 18.1 | 20.7 | 20.9 | 15.1 |
| 8 终端帧间隔 P95，ms | 4.3 | 8.3 | 8.3 | 4.3 |
| 8 终端 CPU，等效逻辑核 | 1.30 | 1.01 | 1.04 | 0.75 |
| 8 终端吞吐，KiB/s | 1023.72 | 1023.79 | 1023.60 | 1023.48 |

前后共24个负载阶段，发送的有效载荷全部收到回执，均无未回执积压、非预期断连、标签点击失败或超过50ms的主线程长任务。两端都完成了目标吞吐，这不是吞吐上限测试。

桌面高负载的部分延迟中位数偏高，网页部分偏低；范围有重叠。例如桌面八终端写入 P95 为6.27–12.37→6.76–11.56ms，网页为7.65–13.33→6.18–10.76ms。不能据此宣称终端整体提速或把差值全部归因于本轮改动。合并优化的稳定收益主要体现在较低的内存及无变化轮询开销。

WebGL 另做了短测和真实上下文丢失检查，能正常完成输出并回退，但短测没有确认性能优势，切换样本也很少。因此本次没有将它设为默认，也没有用短测替代上述默认 DOM 配置的完整测试。

## 兼容性与回归

- 前端176项测试全部通过，TypeScript 检查与生产构建通过。
- 实际 Windows 桌面和可见浏览器均完成中文文件编辑保存、20字节上传、终端输入与输出回执、未保存编辑器保留检查。上传字节由真正的本地测试 HTTP 服务核对。
- Windows WebKit 26.6 补充检查通过两组：正常 API，以及禁用 `randomUUID`、`Array.at`、WebGL2 接口。两组均通过480/800/1440宽度检查、按需页面加载、真实 WebSocket 输出、中文编辑保存、上传和终端操作，未出现页面异常。
- 禁用部分 API 并不能把新版 WebKit 变成旧 Safari。这里仅验证回退路径，**没有完成 Mac 实机运行、安装、窗口生命周期或菜单栏验收**。
- Windows、Mac Intel、Apple Silicon 的构建工作流已加入相同 WebKit 检查和结果截图归档；YAML 已本地解析，远程工作流尚未运行。
- 独立只读代码审查未发现重要源代码问题；补齐了新增操作检查脚本的 CI 路径触发条件。
