# Terminal context attachments

The terminal toolbar explicitly captures either the selection or the currently visible xterm viewport. It does not subscribe the assistant to output or execute input. Captures contain machine ID/label, local terminal tab ID, persistent session ID when available, last known cwd, capture timestamp and source. Unknown cwd is shown explicitly.

Each capture is limited to 150 lines and 12,000 Unicode code points, with truncation recorded; at most three captures can be pending or sent per message. Controls are stripped. Attachments remain in window memory until submitted, and opening the assistant preserves the existing message draft. The user can inspect/remove captures before sending a separate instruction. Standalone terminal windows open a separate companion system window. The desktop places it beside the terminal, resizing/unmaximizing the terminal only if needed to avoid overlap; browser use opens a separate popup. Native attachments use a bounded, per-window memory queue and are drained only by their recipient window. Browser popups use an ephemeral random BroadcastChannel and acknowledge delivery. Neither path stores attachment text in navigation URLs or shared workspace state. Repeated captures reuse the companion window. Closing the assistant preserves chat history and the shared text draft, but unsent terminal attachments remain ephemeral. An older running desktop binary must be restarted with an updated build; refreshing its web page cannot add native window support.

The server independently checks shape, bounds, known machine IDs and restricted machine scope. It scrubs credentials before persistence/model use and labels terminal output as untrusted data, never as authorization. Both Deep Agents and Codex receive the attachment in the explicit user turn. The visible receipt remains plain React text; output is never rendered as HTML. The 4,000-character user instruction limit remains separate. This feature does not expand MCP machine permissions.
