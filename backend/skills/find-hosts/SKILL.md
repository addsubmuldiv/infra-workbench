# 确认机器或分组

用户给出具体名称时，优先把原名称传给 `resolve_target`，明确指定机柜或分组时传 `type="cluster"`。按关键词、硬件或地址筛选机器时用 `find_hosts`。`name` 匹配机器别名和 SSH 连接目标的子串。结果中的 `alias` 是显示名称，`target` 是连接目标；后续操作使用真实 `host_id`。有多个候选时继续核对。

按硬件或地址筛选机器时，不要求设备空闲，不因机器正在训练、离线或采样过期而排除已知硬件。

1. 把描述拆成已知条件，调用 `find_hosts`。以公开的工具 schema 为准，只传有依据的条件；未知卡数、设备种类、显存和空闲要求不要自行补充。
2. 别名/主机名称用 `name`；IP、地址片段和明确的 IP 尾号用 `ip`；卡型号用 `model`；GPU/NPU 用 `kind`；明确的物理卡数用 `card_count`。型号是大小写无关的子串，例如“昇腾950DT”“Ascend 950DT”可取核心型号 `950DT`。不要把 950DT 猜成 910B，也不要给未确认的硬件起别名。
3. “177机器”若看不出是 IP 尾号还是别名，先按 `ip="177"` 查；无匹配时再按 `name="177"` 查，不要把这两个假设同时作为 AND 条件。完整 IP 则直接按 IP 查询。数字片段可能匹配多台，展示实际地址继续核对。
4. 所有条件同时成立。`card_count` 是匹配型号/种类的精确物理卡数；不是设备 ID，不是进程占用卡数，也不是空闲卡数。多 die NPU 按 `card_id` 去重，`device_count` 和 `card_count` 不一定相等。物理卡数未知时不可拿设备数代替。
5. 查看 `items` 和 `uncertain`：前者是匹配候选，后者是信息不足、尚不能排除的候选。只有一项匹配但还有可能相关的 uncertain 时，也不能声称已唯一定位。可用 `get_resources(host_id, refresh=true)` 更新候选硬件后重查；失败仍保留未知说明，不无限刷新。
6. 多项匹配时给出别名、真实 host_id、目标地址、型号和物理卡数，请用户补充区分条件；不擅自选第一项。无匹配时说明实际查询条件，保留型号与卡数要求；可以分别查询单个条件解释哪个条件排除了机器，不擅自放宽后当作原条件匹配。
7. 后续说“八卡那个”“IP结尾177的”“另一台”等时，继承本轮已经明确的机器特征并组合查询。例如先问 950DT，再说八卡，应传 `{"model":"950DT","card_count":8}`。`find_hosts` 不在服务端继承筛选条件，每次都须传完整条件。用户明确换型号或换目标时，去掉不再适用的旧条件。
8. 使用工具返回的真实 host_id 进行下一步。给出匹配依据及采样是否陈旧。查询结果不构成停止进程、执行命令或修改文件的授权；涉及这些操作时读取对应技能并按用户已有授权执行。停止进程前重新核对机器及进程身份。

常见说法与参数示例（不是完整的触发词清单）：

| 用户描述 | 查询参数 |
| --- | --- |
| “950DT 那台机器”“哪台是 Ascend950DT”“找昇腾950DT服务器” | `{"model":"950DT"}` |
| “IP 是 10.23.0.177”“地址包含 23.0.177”“IP 尾号177” | `{"ip":"23.0.177"}` 或 `{"ip":"177"}`，按实际描述填写 |
| “八卡 910B 的机器”“装了八张910B” | `{"model":"910B","card_count":8}` |
| “4 卡 H200”“which server has four H200 GPUs?” | `{"model":"H200","card_count":4}` |
| “177 上那台八卡950DT” | `{"ip":"177","model":"950DT","card_count":8}` |
| “名叫 train-a 的服务器” | `{"name":"train-a"}` |
| “带 NPU 的机器”“昇腾服务器有哪些” | `{"kind":"NPU"}` |

如果用户实际要找“哪台有足够空闲卡可以跑训练”，读取 `find-resources`，按空闲资源查询；如果已经用型号/IP 指定目标，则先定位目标再检查资源。界面限定的机器范围不可扩大，查不到范围外机器时应说明限制。
